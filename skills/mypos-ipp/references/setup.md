# IPP Protocol Setup & Fundamentals

## Protocol Framing

Every IPP message is framed as:

```
[2-byte big-endian length] [PROPERTY=VALUE\r\n] [PROPERTY=VALUE\r\n] ...
```

- The 2-byte header specifies the **total byte length** of the body (all `KEY=VALUE\r\n` pairs combined).
- Each property is on its own line terminated with `\r\n` (CRLF).
- Property names are **ALL CAPS** and **case-sensitive**. `Method` is invalid; `METHOD` is required.

**Mandatory property ordering:**
1. `PROTOCOL` — always first
2. `METHOD` — always second
3. All other properties — any order
4. `DATA` — always last (if present)

Violating the ordering returns `STATUS=2` (SYNTAX ERROR).

## Standard Properties

Every request from caller to terminal:

| Property | Value | Presence | Description |
|----------|-------|----------|-------------|
| `PROTOCOL` | `IPP` | M | Always `IPP` |
| `VERSION` | `202` | M | Use `202` for all current methods; `200` for DISPLAY_TEXT, CHECK_TRANSACTION, OPEN_SETTINGS |
| `METHOD` | (method name) | M | The operation to perform |
| `SID` | UUID | M | Unique session ID generated by caller for each request |

Every response from terminal to caller:

| Property | Presence | Description |
|----------|----------|-------------|
| `PROTOCOL` | ME | Echoed from request |
| `METHOD` | ME | Echoed from request |
| `SID` | ME | Echoed from request |
| `STATUS` | M | Result code (see Appendix I). `0` = success |
| `STAGE` | M | Processing stage (see Appendix II) |
| `TIMEOUT` | O | Seconds until next response (0 = final) |

ME = Mandatory Echo (value echoed from the request).

## Protocol Versions

| Version | Notes |
|---------|-------|
| `100`–`106` | Legacy versions |
| `200` | Basic current version |
| `201` | Intermediate version |
| `202` | Current; adds PING, REBOOT, GIFTCARD_*, PAYMENT_REQUEST*, SEND_LOG |

Version 202 methods (PING, REBOOT, GIFTCARD_ACTIVATION, GIFTCARD_DEACTIVATION, PAYMENT_REQUEST, PAYMENT_REQUEST_REMINDER, SEND_LOG) work **only on Q20 and K300 terminal models**.

## Operation Modes

### Cash Register mode (`OWN_CONNECTION=1`)
The terminal has its own network (WiFi or SIM) and communicates directly with the acquiring host. The caller just sends requests and waits for stage responses. No network proxying required.

### Slave mode (`OWN_CONNECTION=0`)
The **caller** provides network connectivity. The terminal cannot reach the acquiring host on its own.

In Slave mode:
- STAGE=1 response includes `IP`, `PORT`, and `CHAIN` — the acquiring host address and SSL certificate fingerprints.
- STAGE=4 response includes `DATA` — a binary blob the caller must forward to the acquiring host verbatim.
- The caller opens a TCP connection to `IP`:`PORT`, sends the DATA bytes, receives a response, then sends that response back to the terminal as a new STAGE=4 message with the `DATA` property set to the host response.
- This STAGE=4 loop repeats until STAGE=5 arrives.
- **DATA bytes must not be altered in any way** — no headers, no framing.

## SID — Session ID

Generate a new UUID for each request. The terminal echoes the SID back in all response stages. For methods that reference a previous transaction, use `SID_ORIGINAL` to reference the prior session's SID.

Example SID: `126ca831-93d2-4dfc-ab1f-0cce1d0abe9e`

## SSL Certificate Management (Slave mode only)

The terminal maintains two certificate chains:
- `PRIMARY_CHAIN` — used for all methods except UPDATE
- `SECONDARY_CHAIN` — used for the UPDATE method

Each chain is a sequence of up to 4 fingerprints, each exactly 20 bytes, separated by `;`.

When the terminal returns a new fingerprint in any response, the caller must call `GET_CERTIFICATE` to retrieve the corresponding DER-encoded certificate. See `references/terminal-lifecycle.md`.

## Stage Flow Summary

| Stage | Name | Description |
|-------|------|-------------|
| `1` | CHECK REQUEST DATA | Terminal validated request; no customer interaction needed |
| `2` | CARD HANDLE | Terminal displaying "Present card" screen |
| `3` | PIN HANDLE | Terminal displaying "Enter PIN" screen |
| `4` | PROCESSING DATA | Slave mode: proxy DATA to/from acquiring host |
| `5` | PROCESSING OUTCOME | Final result after host communication |
| `11` | USER_PRESENT_CARD | Notification: customer presented card |
| `12` | USER_PRESENT_DCC | Notification: DCC currency choice shown |
| `13` | USER_PRESENT_PIN | Notification: customer entering PIN |
| `14` | USER_SELECTED_DCC | Notification: customer selected DCC option |
| `101` | STAGE_CANCEL | Cancel an ongoing VENDING_PURCHASE (or PURCHASE/REFUND/CASH_ADVANCE with sw≥3.45) |

Stages 11–14 are **optional notification stages** — the caller may receive them but they are not required to be handled for correct operation.

## Key Error Recovery

| STATUS | Meaning | Action |
|--------|---------|--------|
| `25` | ACTIVATION REQUIRED | Call ACTIVATE then UPDATE |
| `26` | MANDATORY UPDATE REQUIRED | Call UPDATE |
| `20` | NOT COMPLETED LAST TX | Call COMPLETE_TX for the previous transaction |
| `36` | DEACTIVATION NOT FINISHED | Retry DEACTIVATE |
| `100` | OK with additional info | Call GET_STATUS |
| `41` | REMOTELY ACTIVATED (from PING) | Call UPDATE |
